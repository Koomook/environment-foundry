# AI가 칩 설계를 어떻게 배우는가 — 공개 콘텐츠 경계

이 문서는 기존 연구를 LinkedIn·공개 웹·교육 콘텐츠로 바꾸기 위한
편집 경계다. 문서 자체는 공개 승인 전까지 `internal-only`이며, 아래
`공개 가능`으로 분류한 내용만 별도 원고로 옮길 수 있다.

## 한 문장 공개 thesis

> **AI는 칩 설계 파일을 많이 읽는 것만으로 칩 설계를 배우지 않는다.
> 설계안을 내고, 실행 가능한 도구로 돌려 보고, 기능과 물리 조건을
> 통과했는지 채점받는 반복 속에서 배운다.**

더 짧은 버전:

> **칩 설계 AI에게 필요한 것은 답안지가 아니라, 실험하고 채점받을 수
> 있는 실습실이다.**

이 thesis는 “AI가 이미 칩 전체를 자율 설계한다”는 주장이 아니다.
현재 공개 실험으로 말할 수 있는 범위는 작고 경계가 분명한 설계 작업에서
실행 피드백이 오류를 걸러 내고 후보를 비교하게 만든다는 것이다.

## 공개 메시지의 논리

1. 칩 설계는 그럴듯한 코드를 쓰는 문제가 아니다.
2. 먼저 기능적으로 맞아야 하고, 그다음 속도·전력·면적·제조 조건을
   함께 만족해야 한다.
3. 이 조건들은 언어모델의 말이 아니라 simulator, formal checker,
   synthesis, place-and-route 같은 실행 도구가 확인한다.
4. 따라서 좋은 학습 단위는 파일 하나가 아니라
   `당시 상태 → 설계 변경 → 도구 실행 → 결과 → 채택 또는 되돌리기`다.
5. 공개 합성 실험에서도 보이는 예제만 맞힌 잘못된 설계는 숨은 검사에서
   무너졌고, 기능을 통과한 설계끼리는 합성 결과로 비교할 수 있었다.
6. 그러나 이 결과는 실제 공정, 상용 signoff, 생산 수율 또는 실리콘
   성능을 입증하지 않는다.

## 공개 가능 / 수정 후 공개 / 제외

### 1. 그대로 공개 가능한 내용

다음은 공개 문서·오픈소스 도구·합성 실험으로 뒷받침되며 회사의 영업
전략을 드러내지 않는다.

| 내용 | 공개 방식 | 필수 한계 표시 |
|---|---|---|
| 칩 설계는 기능 정합성 이후 PPA와 제조 조건을 함께 최적화하는 제약 탐색이라는 설명 | 쉬운 비유와 간단한 식으로 공개 | 하나의 점수로 모든 품질을 환원하지 않기 |
| corpus와 executable environment의 차이 | “교과서와 실습실” 비유 | 데이터가 불필요하다는 뜻은 아님 |
| simulator fidelity ladder | RTL simulation → formal → synthesis → physical design → signoff → silicon 순서 | 한 도구가 전체 현실을 재현한다고 말하지 않기 |
| 좋은 학습 episode의 일반 구조 | 상태 → 행동 → 실행 → 결과 → 채택/되돌리기 | 실제 회사 데이터 보유를 암시하지 않기 |
| 공개·합성 RTL 실험의 5단계 학습 | 아래 공개 서사 사용 | 생산 칩이나 고객 설계 결과가 아님을 명시 |
| visible-test gaming과 hidden test의 필요성 | 교육적 예시로 공개 | hidden test만으로 완전한 검증이 되지는 않음 |
| 기능 검사를 hard gate로 두고 그 뒤에 품질을 비교하는 원칙 | 공개 가능 | 합성 cell 수는 실제 면적·전력과 동일하지 않음 |
| 권한에 따라 AI가 볼 수 있고 할 수 있는 일이 달라진다는 일반 원칙 | 공개 가능 | 구체적 데이터 획득·계약 전략은 제외 |
| `OBSERVED`와 `NOT YET` 구분 | 적극 공개 | 가능성과 증거를 혼동하지 않기 |
| 오픈소스 simulator·synthesis·physical-design 도구와 논문 링크 | 중립적 학습 자료로 공개 | 제품 추천이나 성능 보증으로 쓰지 않기 |

### 2. 일반화·비식별화한 뒤 공개 가능한 내용

| 원래 내용 | 공개용 변환 | 제거할 것 |
|---|---|---|
| rights-valid environment | “설계 파일마다 열람, 실행, 평가, 학습 허용 범위가 다르다” | 내부 권리 매트릭스, 보유기간, 삭제 SLA, 계약 기본값 |
| partner-side execution | “민감한 설계는 외부로 옮기지 않고 통제된 환경에서 평가할 수 있다” | 파트너 유형, 배포 방식, 협상 순서 |
| commercial tool/PDK reality gap | “공개 도구의 결과는 실제 공정용 도구에서 다시 검증해야 한다” | 특정 공급자, 라이선스 협상, 비용 구조 |
| five-iteration artifact | “작은 합성 ALU 실험”으로 소개 | 로컬 경로, 저장소 구조, 내부 workstream, 제품명 |
| 실험 수치 | 구체적 수치는 부록에서 재현 가능할 때만 사용 | 상대 우위를 실제 칩 성능처럼 표현하는 문장 |
| 여러 grader의 필요성 | 기능·물리·비용을 순차 확인하는 원리로 공개 | 내부 점수식과 go/no-go threshold |
| prospective validation | “오프라인에서 좋았던 순위가 새 문제에서도 유지되는지 확인해야 한다” | 실제 검증 일정, episode 목표량, 구매 조건 |

### 3. 공개 콘텐츠에서 제외할 내용

아래는 사실 여부와 무관하게 이 공개 교육물의 목적에 필요하지 않고 회사
전략·시장 진입·영업 가설을 노출한다.

- Environment Foundry라는 회사명, 제품명, 내부 조직명, workstream ID,
  owner, proof ladder, 로컬 저장 경로.
- 한국 또는 해외의 특정 반도체 회사명, 디자인하우스·IP·장비·후공정
  회사 후보, 그 회사의 참여 가능성에 대한 추정.
- 한국 중소 팹리스가 첫 시장인지, 어느 파트너 유형을 우선할지, 한국
  locality가 access 또는 성능에 유리할지에 관한 가설.
- “첫 파트너”, “다음 환경”, “병렬 옵션” 같은 시장 진입 순서.
- 90일 계획, 주차별 실행안, 목표 episode 수, 인터뷰 수, 성능 개선
  threshold, stop rule.
- buyer-written specification, paid pilot, 가격, 비용 부담, willingness to
  pay, 단위경제, 판매 주체와 구매 부서.
- 데이터 획득 우선순위와 partner-side 반출 필드, 계약 협상 문구, 권리
  기본값, retention/deletion 운영안.
- 고객 RTL/GDS, PDK, wafer map, fab recipe 등 구체적인 획득 대상과
  획득 금지 목록. 공개 교육물에서는 “민감한 설계·공정 데이터”로만
  일반화한다.
- 경쟁 제품·상용 EDA 공급자 이름과 경쟁·종속 위험 분석.
- “방어 가능한 자산”, “data flywheel”, “컨설팅으로 붕괴할 위험” 등
  회사의 사업모델 thesis와 반론.
- 특정 회사가 어떤 데이터나 내부 reference design을 보유할 것이라는
  추론.
- 비공개 연락처, 개인 이름, 고객 관계, 대화, 계약 또는 접근 가능성을
  암시하는 모든 표현.

## 쉬운 한국어 설명 구조

### 제목 후보

1. **AI는 칩 설계를 어떻게 배우는가**
2. **칩 설계 AI에게 필요한 것은 데이터보다 ‘실습실’이다**
3. **AI에게 칩 설계를 가르치는 다섯 개의 시험대**

1번이 가장 중립적이다. 2번을 쓰면 본문에서 “데이터가 필요 없다는 뜻은
아니다”라고 바로 보정해야 한다.

### 도입 — 코딩과 칩 설계는 무엇이 다른가

쉬운 문장:

> AI가 코드를 그럴듯하게 쓰는 것과, 실제로 동작하는 칩을 설계하는 것은
> 다릅니다. 칩은 한 군데만 틀려도 동작하지 않을 수 있고, 기능이 맞아도
> 너무 느리거나 전력을 많이 쓰거나 실제로 만들 수 없으면 실패입니다.

질문으로 시작할 경우:

> AI가 만든 회로가 “맞다”는 것을 누가 확인할까요?

### 1장 — 교과서보다 실습실

비유:

- 설계 파일과 논문은 **교과서**다.
- simulator와 checker는 **실습 장비와 시험관**이다.
- test와 constraint는 **시험 문제와 안전 규칙**이다.
- grader는 **채점표**다.
- versioned checkpoint는 **같은 조건으로 다시 시작할 수 있는 실험대**다.

핵심 문장:

> AI는 정답 예시를 보는 것뿐 아니라, 자기가 낸 답을 실행해 보고 왜
> 실패했는지 확인할 수 있어야 합니다.

### 2장 — 칩은 한 번이 아니라 여러 번 시험한다

다음 사다리를 한 문장씩 설명한다.

1. **RTL simulation**: 입력을 넣었을 때 논리 동작이 예상과 같은가?
2. **Formal verification**: 몇 개 예시가 아니라, 정한 조건 전체에서
   반드시 지켜지는가?
3. **Synthesis**: 논리 코드가 실제 게이트 구조로 바뀔 수 있는가?
4. **Physical design**: 게이트와 배선을 실제 칩 면적 안에 놓고 연결할 수
   있는가?
5. **Signoff**: 시간, 배선, 전력, 제조 규칙을 최종 통과하는가?
6. **Silicon measurement**: 만들어진 칩도 예상대로 작동하는가?

핵심 문장:

> 앞 단계의 점수가 좋아도 다음 단계에서 순위가 바뀔 수 있습니다. 그래서
> 싼 시험으로 많이 연습하고, 비싼 시험으로 그 판단이 현실에서도
> 맞는지 확인해야 합니다.

### 3장 — AI가 배워야 할 데이터의 모양

파일 목록 대신 한 episode를 보여 준다.

```text
현재 회로와 실패 보고서
→ AI가 한 가지 변경
→ 도구가 다시 실행
→ 기능·속도·면적 결과
→ 변경을 채택하거나 되돌림
```

쉬운 설명:

> 중요한 것은 완성된 정답 파일 하나가 아니라, 어떤 상황에서 무엇을
> 바꿨고 그 결과가 어땠는지가 연결된 기록입니다.

권리 설명:

> 칩 설계에는 민감한 지식재산이 많습니다. 볼 수 있는 정보, 실행할 수
> 있는 도구, 평가에 쓸 수 있는 결과, 학습에 재사용할 수 있는 기록은
> 서로 다른 허가가 필요합니다.

여기서 특정 데이터 종류, 회사, 계약 방식으로 들어가지 않는다.

### 4장 — 작은 공개 실험에서 배운 다섯 단계

기존 실험은 다음처럼 단순화한다.

1. **문법 검사**: 깨진 회로 코드는 실행 전에 탈락했다.
2. **보이는 문제의 함정**: 몇 개 예제만 맞춘 잘못된 회로도 처음에는
   통과했다.
3. **숨은 검사**: 입력 조합을 넓히자 그 회로가 틀렸음이 드러났다.
4. **기능 우선**: 올바른 회로만 남긴 뒤 합성 결과를 비교했다.
5. **새 조건 확인**: 회로의 크기를 바꿔도 같은 판단이 유지되는지 다시
   검사했다.

공개 가능한 결론:

> 작은 실험이지만, “생성 → 실행 → 숨은 검증 → 품질 비교 → 새 조건에서
> 재검증”이라는 학습 구조는 확인할 수 있었습니다.

반드시 붙일 한계:

> 이 실험은 합성한 교육용 회로에서 진행됐습니다. 실제 공정의 배치배선,
> 상용 signoff, 생산 수율 또는 실리콘 성능을 검증한 결과는 아닙니다.

### 5장 — 아직 모르는 것

공개 콘텐츠의 신뢰를 만드는 장이다.

- 공개 도구에서 좋아진 설계가 실제 공정에서도 좋아지는가?
- 한 종류 회로에서 배운 방법이 다른 회로에도 통하는가?
- 숨은 검사가 빠뜨린 오류를 AI가 악용하지 않는가?
- 물리 설계 결과와 실제 제작된 칩의 결과가 얼마나 일치하는가?
- 같은 도구 시간과 계산량에서 단순 탐색이나 인간 전문가보다 나은가?

마무리:

> 칩 설계 AI의 핵심 질문은 “얼마나 많은 파일을 읽었나”가 아닙니다.
> “어떤 행동을 할 수 있고, 어떤 현실 검사를 통과했으며, 그 판단이 새
> 문제에서도 맞았는가”입니다.

## LinkedIn용 7단락 골격

1. **Hook** — “AI가 만든 회로가 맞다는 것을 누가 확인할까?”
2. **오해** — 칩 설계 파일을 많이 모으면 자동으로 칩 설계 AI가 된다는
   생각.
3. **전환** — 필요한 것은 교과서뿐 아니라 실행·채점 가능한 실습실.
4. **사다리** — simulation, formal, synthesis, physical design, signoff,
   silicon을 쉬운 말로 연결.
5. **작은 실험** — 보이는 테스트를 속인 회로가 숨은 검사에서 실패한
   이야기.
6. **한계** — 공개 합성 회로에서 관찰했을 뿐 실제 칩 성능은 아직
   입증하지 못함.
7. **Close** — “AI가 칩 설계를 배우는 최소 단위는 파일이 아니라
   행동과 결과가 연결된 실험이다.”

각 단락은 2–4문장으로 제한한다. 회사·시장·파트너 이야기는 후속 공개
승인이 있더라도 이 교육 포스트와 섞지 않는다.

## 공개 전 문장 수준 체크리스트

### 사실과 증거

- [ ] `OBSERVED`, `HYPOTHESIS`, `NOT YET`이 문장에서 구분되는가?
- [ ] 합성/open experiment를 production 또는 silicon 결과처럼 쓰지
      않았는가?
- [ ] 합성 cell 수를 실제 면적·전력·수율로 번역하지 않았는가?
- [ ] vendor의 성능 주장을 독립 검증된 사실처럼 쓰지 않았는가?
- [ ] 모든 기술 설명이 공개 문서 또는 공개 artifact로 재현 가능한가?

### 기밀과 전략

- [ ] 회사명·제품명·내부 조직·workstream·로컬 경로를 제거했는가?
- [ ] 특정 반도체 회사와 파트너 가능성을 암시하지 않는가?
- [ ] 한국 중소 팹리스, 디자인하우스, IP, 장비사를 영업 대상으로
      평가한 흔적이 없는가?
- [ ] 90일 계획, 목표 수량, 개선 threshold, stop rule이 없는가?
- [ ] 데이터 획득 순위, 계약 기본값, 반출 필드, 구매가설이 없는가?
- [ ] 내부 경쟁·사업모델·방어력 분석이 없는가?

### 독자 이해

- [ ] 첫 3문장 안에 “실행하고 채점받는 반복”이 나오는가?
- [ ] 데이터가 불필요하다는 오해를 막았는가?
- [ ] simulator를 하나의 완벽한 현실 복제물처럼 말하지 않는가?
- [ ] 전문용어마다 한 줄짜리 쉬운 설명이 있는가?
- [ ] 마지막에 아직 모르는 것을 최소 세 가지 남겼는가?
